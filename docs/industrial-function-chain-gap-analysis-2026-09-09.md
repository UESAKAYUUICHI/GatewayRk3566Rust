# 网关与平台实际功能链路工业化评估

评估时间：2026-09-09  
评估范围：

- 网关项目：`GatewayRk3566Rust`
- 接入服务：`park-energy-access`
- 数据服务：`park-energy-data`
- 平台服务：`park-energy-platform`
- 平台前端：`park-energy-web-vue`

本文从“真实工业项目能不能交付、能不能维护、出问题能不能定位”的角度梳理功能链路和缺陷。结论基于当前代码结构、已有文档、近期 RK3568 实机部署记录与业务链路阅读；未做完整云端联调压测，因此涉及稳定性、性能和安全合规的判断需要后续用现场测试数据确认。

## 1. 总体结论

当前项目已经不再是纯前端演示玩具，主链路已经具备真实工业网关的雏形：

1. 网关侧已有真实 RS485/Modbus RTU 采集、SQLite 本地状态、Outbox 缓存、MQTT QoS1 上报、NetworkManager Wi-Fi 控制、Kiosk 前端部署。
2. 接入服务已有 MQTT 入站处理、网关身份校验、原始报文落库、去重、RabbitMQ 转发、命令下发与命令响应记录。
3. 数据服务已有 RabbitMQ 消费、报文解析、设备物模型映射、时序写入、实时缓存、小时/日/分时统计、质量窗口、告警评估。
4. 平台服务已有档案、设备绑定、网关配置同步、物模型、告警规则、权限、计费、合同等业务模块。
5. 平台前端已有较完整的管理页面，但部分业务动作仍需要用“端到端证据链”验证，而不能只看页面按钮是否存在。

从工业交付角度看，最大风险不是页面功能，而是“配置、数据、告警、命令、运维”这几条链路还缺少闭环审计、回滚、追踪、失败恢复和安全加固。也就是说，现在已经能跑通一套展示型/试点型系统，但距离可长期交付给现场运维人员使用，还需要补齐工程化能力。

## 2. 当前端到端业务链路

### 2.1 现场采集链路

当前设计是：

```text
电表/设备
  -> RS485 总线
  -> Modbus RTU 轮询
  -> 网关本地解析/缓存
  -> Outbox 待发队列
  -> MQTT QoS1
  -> park-energy-access
  -> RabbitMQ
  -> park-energy-data
  -> IoTDB/Redis/MySQL
  -> park-energy-platform / park-energy-web-vue
```

代码证据：

- 网关设计文档定义了 RS485、Modbus RTU、Outbox、MQTT QoS1、NetworkManager 和 systemd/kiosk 部署：`docs/DESIGN.md`
- 网关真实化记录确认了 RS485 总线模型、串口参数、Wi-Fi 真实控制和前端方向适配：`docs/production-readiness.md`
- 实机记录确认 RK3568 板端运行 Ubuntu 24.04、4 核 Cortex-A55、4G Swap、网关服务、Chromium kiosk、NetworkManager、`REDMI K90 Ultra` Wi-Fi、`/dev/ttyS3` RS485 通道：`docs/current-rk3568-status-2026-09-09.md`

当前状态：

- 代码已经支持“一条 RS485 通道挂多台设备”，按 `channel_id + modbus_addr` 定位设备。
- 平台同步服务也校验同一 RS485 通道内 Modbus 地址唯一，地址范围 `1..247`。
- 近期实机记录中平台同步到本地的电表有 `WZBC-LS2-M-325`、`WZBC-LS2-M-326`，但尚未采到在线读数。

主要缺口：

- 真实电表通讯还没有形成稳定证据，例如连续读数、异常断线、恢复、错地址、A/B 反接、波特率错误的诊断结果。
- 当前质量判断更多停留在“数值是否异常、时间是否合理”，缺少现场电气问题诊断。
- 485 总线的工程细节还需要补：终端电阻、偏置电阻、线缆长度、屏蔽接地、总线冲突、响应超时分布、重试退避策略。

### 2.2 网关到接入服务链路

当前设计是：

```text
gateway/{gatewayId}/data/upload
gateway/{gatewayId}/status/heartbeat
gateway/{gatewayId}/alarm/up
gateway/{gatewayId}/cmd/response
```

接入服务 `GatewayDataUploadHandler` 的处理逻辑较清晰：

1. 解析网关上传 JSON。
2. 根据 topic 中的网关 ID 与 payload 中的 `gatewaySn` 校验网关。
3. 用 `gatewayId + messageId` 做重复判断。
4. 原始报文先入库。
5. 校验上报中每个 meter 是否属于该网关。
6. 未登记设备进入发现设备/暂存逻辑。
7. 已登记设备转发到 RabbitMQ。
8. 转发成功则标记 `FORWARDED`，失败则标记 `MQ_FAILED`。

这是比较接近生产系统的做法，尤其是“先落原始报文，再异步转发”的思路是对的。

主要缺口：

- MQTT 认证和 TLS 从代码/配置看还不够硬。网关配置中存在明文 MQTT 地址、用户名、密码，且当前端口为 1883。
- `messageId` 去重依赖接入层存储和数据层存储共同正确工作，需要确认数据库唯一约束、Rabbit 重投、服务重启后的幂等是否全部成立。
- 原始报文重放已有任务雏形，但需要补可观测性：哪些消息卡住、重试几次、最后去了哪里、是否进入死信。
- 接入服务中存在内存仓库实现，适合测试，但生产环境必须明确禁止误用。

### 2.3 接入服务到数据服务链路

当前设计是：

```text
park-energy-access
  -> RawDataProducer
  -> RabbitMQ raw-data / alarm queue
  -> park-energy-data RawElectricDataConsumer
  -> DataIngestService
```

数据服务 `DataIngestService` 当前做了：

- 数据入库幂等 claim。
- 每个 meter 的 item 级别幂等。
- 网关/设备上报限流。
- 设备档案查找。
- 物模型点位定义与寄存器映射。
- 解析点值。
- 点值范围校验。
- 写入时序库。
- 保存实时快照。
- 更新小时、日、分时统计。
- 更新采集质量窗口。
- 触发告警规则评估。

这一层的业务骨架很完整，是目前项目里“最像工业数据平台”的一部分。

主要缺口：

- 报文、设备、测点、统计、告警是多个存储写入，虽然方法有事务，但时序库写入、Redis 写入、MySQL 写入之间不是天然分布式事务。需要明确失败补偿策略。
- `quality != 0` 当前会直接拒绝整台 meter 的样本，工业场景中更常见的是“入库但标记质量”，否则会丢失故障期间的重要证据。
- 点值范围校验目前比较硬编码，如电压、电流、频率范围；后续应由物模型/设备型号/现场 CT/PT 倍率驱动。
- 统计更新放在实时入库链路中，吞吐上去后可能拖慢消费，需要评估是否拆为异步聚合。
- 质量窗口和缺失监测已有结构，但需要用现场采样周期、网络延迟和仪表响应特性重新标定阈值。

### 2.4 平台管理链路

平台服务已有较多业务模块：

- 设备档案、组织、空间、设备类型、物模型。
- 网关档案、设备绑定、发现设备绑定。
- 网关配置同步：`/api/platform/edge/config`
- 告警规则、告警事件。
- 接入服务代理：网关状态、原始报文、命令、发现设备。
- 数据质量、实时数据、历史统计。
- 计费、租户、合同、电价方案、账单。
- 权限与操作审计基础。

平台侧 `EdgeGatewaySyncService` 是一个关键点：网关通过 `X-Gateway-Sn` 和 `X-Gateway-Secret` 拉取自己的设备、通道、物模型点位，并通过 `/ack` 回传应用结果。它已经校验：

- 网关凭据。
- 设备 Modbus 地址范围。
- 同一 `channelId + modbusAddr` 不重复。
- 设备必须绑定 RS485 通道。
- 采集周期范围。
- 物模型必须存在可采集测点。

主要缺口：

- 配置同步是“网关拉取”的基础版，还缺少平台侧变更审批、版本 diff、灰度发布、失败回滚、设备级应用结果。
- 网关应用配置失败时，目前只看到状态 ACK，没有看到完整的错误证据、失败设备列表、自动回滚策略。
- 设备档案、物模型、数据服务映射之间存在多个来源，一旦不一致，会出现“平台看着配置正确，数据服务解析失败”的问题。
- 告警规则同步到网关后，本地告警与平台告警的生命周期需要统一，否则可能出现本地确认了、平台仍未确认，或平台恢复了、网关仍显示活动告警。

### 2.5 平台前端链路

平台前端项目 `park-energy-web-vue` 已经有管理页面和 API 封装，包括档案、设备详情、数据质量、告警、计费、能效等页面。从项目结构看，它更像“管理平台前端”，而网关前端是“现场触屏运维终端”。

主要缺口：

- 需要对平台前端所有按钮做一次动作矩阵：页面按钮、调用 API、后端服务、数据库变更、权限点、失败提示、操作日志。
- 前端若只展示远端代理数据，但没有清晰提示数据更新时间、同步状态和失败原因，现场运维会误判。
- 计费和合同相关页面如果要进入真实项目，必须能追溯每笔账单使用了哪个采样窗口、哪个设备、哪个倍率、哪个电价版本。

## 3. 当前比较扎实的部分

### 3.1 架构分层是对的

网关 Rust 项目按 `gw-proto`、`gw-core`、`gw-store`、`gw-collector`、`gw-link`、`gw-network`、`gw-web`、`gw-ui` 拆分，方向比较清楚。采集、上报、网络和 UI 没有全部揉成一个文件，这对后续长期维护有价值。

### 3.2 数据上报不是简单直发

网关设计中有 Outbox，接入服务也先保存原始报文再转发 RabbitMQ。这个设计能处理断网、重放、幂等，是工业网关必须有的基本能力。

### 3.3 485 多设备认知已经修正

当前网关文档和平台同步服务都已经按 RS485 总线模型处理，不再把“一条串口只能绑一台设备”当成前提。

### 3.4 Wi-Fi 已走真实系统能力

网关网络模块通过 NetworkManager/nmcli 读写真实 Wi-Fi，而不是前端假状态。之前“实际连 REDMI K90 Ultra，但程序显示 Laplace_5G”的问题也已经定位为 WebSocket 快照没有刷新 Wi-Fi 状态。

### 3.5 平台已有工业管理雏形

平台不是只有首页看板，已经存在设备档案、物模型、配置同步、数据质量、告警、命令、计费和权限模块。后续工作重点应转向“闭环”和“证据”，而不是继续堆页面。

## 4. 工业项目视角的主要缺陷

### P0：必须优先解决

1. 真实 RS485 采集尚未闭环验收  
   目前实机记录中两台电表仍未在线。没有真实连续采样，后面的统计、告警、计费都是空中楼阁。必须先用真实电表拿到稳定读数。

2. 安全基线不足  
   当前可见配置中存在明文 MQTT 凭据，MQTT 端口看起来是 1883，板端曾使用 root 密码 SSH。工业现场至少需要 MQTT TLS/认证、非 root 运行、禁用弱口令、密钥文件权限、日志脱敏。

3. 配置下发缺少强闭环  
   平台能生成配置，网关能拉取配置，但还需要“版本、审批、应用结果、失败设备、回滚、审计”完整链路。否则现场一改配置导致停采，很难快速恢复。

4. 数据链路缺少全链路追踪  
   需要用同一个 trace key 串起：网关本地 Outbox ID、`messageId`、接入 rawLogId、Rabbit 消息、数据 ingest event、设备 item、时序写入、实时缓存、统计记录、告警事件。

5. 告警生命周期不统一  
   网关本地告警、平台告警、数据服务评估告警、接入服务告警 ACK 之间需要统一状态机。工业项目中告警必须区分：发生、持续、恢复、确认、关闭、误报、抑制、升级。

### P1：进入试点前应解决

1. 设备物模型与测点映射缺少版本治理  
   平台有物模型版本，但数据服务和网关使用时需要记录“本次数据按哪个模型版本解析”。否则模型升级后，历史数据解释可能变掉。

2. 现场调试能力不足  
   网关前端需要提供“单设备立即读取、原始寄存器查看、通讯耗时、异常码、连续失败次数、最近成功时间、485 参数探测”的工程视图。

3. OTA 与回滚缺失  
   当前部署更接近手工覆盖 dist 和服务程序。工业网关需要版本包、校验、安装前检查、失败自动回滚、升级日志、远程诊断包。

4. 断网/断电压力测试不足  
   Outbox 设计是对的，但需要验证：断网 24 小时、断电重启、MQTT broker 重启、RabbitMQ 不可用、数据服务宕机后恢复，是否不丢、不乱、不重复计费。

5. 运维监控不足  
   需要采集网关 CPU、内存、磁盘、温度、进程、网络、MQTT、Outbox 深度、串口错误率，并上送平台形成趋势。

### P2：长期产品化需要解决

1. 多协议扩展  
   当前核心是 Modbus RTU。真实项目可能需要 DL/T645、Modbus TCP、IEC 104、BACnet、厂商私有协议。现在架构有 trait 基础，但产品层还没形成协议插件机制。

2. 多租户和权限细节  
   平台有权限基础，但需要检查每个列表、详情、导出、命令、配置变更是否全部按组织/网关/设备范围过滤。

3. 计费级证据链  
   如果要做收费结算，必须有冻结账期、读数快照、倍率版本、电价版本、人工修正记录、审批记录、重算记录和不可篡改审计。

4. UI 与工业现场一致性  
   网关前端现在为了竖屏屏幕做了视觉旋转，这能解决当前触摸问题，但长期最好还是形成“原生竖屏布局”和“横屏布局”两套响应式设计，而不是一直靠旋转视觉坐标。

## 5. 分链路缺陷清单

| 链路 | 当前能力 | 主要缺陷 | 建议动作 |
|---|---|---|---|
| 设备接入 | RS485/Modbus RTU，多设备总线模型 | 未完成真实表连续采样验收 | 先完成 325/326 电表现场读数、错误码、波特率、地址验证 |
| 网关采集 | 本地设备、通道、Outbox、MQTT | 对电气层故障诊断弱 | 增加原始帧、异常码、耗时、失败次数、单点读取 |
| 网关配置 | 本地配置 + 平台拉取 | 缺版本 diff、回滚、失败设备清单 | 配置 revision 细化到设备和模型版本 |
| Wi-Fi | NetworkManager 真实控制 | 弱网、错密码、漫游、隐藏网络处理不足 | 增加连接阶段状态、错误分类、已保存网络管理 |
| 接入服务 | MQTT 入站、raw 落库、Rabbit 转发 | 安全与重放观测不足 | 启用 TLS/认证、死信看板、重放审计 |
| 数据服务 | 消费、解析、时序、实时、统计、告警 | 多存储一致性和质量策略待加强 | 引入补偿任务、质量标记入库、异步统计 |
| 平台服务 | 档案、同步、命令、计费、权限 | 配置/命令/告警闭环不够完整 | 建立操作工单式闭环和审计 |
| 平台前端 | 管理页面较完整 | 按钮到后端链路需要逐项验收 | 建立按钮/API/权限/日志矩阵 |
| 部署运维 | systemd/kiosk/实机部署 | OTA、回滚、监控、日志归集不足 | 建立生产部署包和运维看板 |
| 安全 | 有网关 secret 概念 | 明文密钥、弱口令、无 TLS 风险 | 密钥加固、证书、最小权限、SSH 加固 |

## 6. 建议的下一阶段里程碑

### M1：真实采集验收

目标：证明网关不是页面工程，而是真的能稳定采集现场仪表。

验收项：

- 325 电表和 326 电表连续采样不少于 2 小时。
- 每台设备记录最近成功时间、连续失败次数、平均响应耗时。
- 能看到原始寄存器值与解析后测点值。
- 拔掉 485 线、改错地址、断 Wi-Fi、重启服务后，状态变化符合预期。

### M2：端到端数据追踪

目标：任意一条采样数据都能从网关追到平台页面。

验收项：

- 网关 Outbox 记录 `messageId`。
- access 原始报文保存 rawLogId。
- data 记录 ingest event 和 item。
- 时序库能查到同一设备同一时间点的数据。
- 平台前端能显示同一条数据的更新时间。
- 失败消息能看到失败原因和重放入口。

### M3：配置闭环

目标：平台修改设备/模型/采集周期后，网关可控地应用。

验收项：

- 平台每次配置变更生成 revision。
- 网关拉取后显示待应用 diff。
- 应用成功回传设备级结果。
- 应用失败保留旧配置并回传错误。
- 平台能看到哪个网关停留在哪个 revision。

### M4：安全与运维加固

目标：达到可放现场长期运行的最低安全与运维要求。

验收项：

- MQTT 使用 TLS 或至少受控内网认证。
- 网关非 root 运行，SSH 禁用弱口令或改密钥登录。
- 密钥文件权限受控，前端不返回敏感密钥明文。
- systemd watchdog、日志滚动、磁盘水位、CPU 温度、内存、服务健康上送平台。
- 有诊断包下载能力，包含配置摘要、日志、网络、串口、Outbox、版本信息。

### M5：计费/报表可信化

目标：如果平台要承担计费或能源结算，必须让数据可审计。

验收项：

- 账期冻结。
- 电价版本冻结。
- 倍率/CT/PT 版本冻结。
- 读数快照不可被后续模型修改影响。
- 人工修正有审批和原因。
- 重算账单有旧版本和新版本对比。

## 7. 最优先整改清单

建议按以下顺序推进：

1. 先把 325/326 两台真实电表采起来，拿到稳定读数。
2. 给网关前端增加“现场调试页”：单次读取、原始寄存器、错误码、耗时、最近 20 次通讯结果。
3. 建立 `messageId` 全链路追踪页面或接口。
4. 把网关配置同步改成带 diff、设备级 ACK、失败回滚。
5. 把 MQTT 凭据和 SSH/系统权限做安全加固。
6. 对平台前端做按钮/API/权限/日志矩阵验收。
7. 做断网、断电、服务重启、RabbitMQ 停机、数据服务停机的恢复测试。
8. 为 OTA、诊断包、日志归集、系统指标上送补生产运维能力。

## 8. 一句话判断

当前系统已经具备“真实网关 + 云平台”的主要骨架，适合继续做实机试点；但它还不是一个可以直接交付长期无人值守现场的工业产品。下一步不要再优先堆 UI，而要优先把真实采集、端到端追踪、配置闭环、安全加固和运维恢复能力做扎实。
